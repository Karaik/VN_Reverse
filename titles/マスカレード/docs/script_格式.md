# Himauri 脚本格式（写回导向版）

## 作用范围

本文件只保留与“静态文本写回”直接相关的事实。

以下内容已经从主文档移出：

- 深层 branch / switch 状态机分析
- type7 / type8 的业务语义细节
- 与文本写回无直接关系的研究型统计

更早的研究性说明已从主文档移出，不再作为默认入口。

## 载体

- 头部固定为 `Himauri\0`
- `0x08..0x0A`：`u24be` 声明大小
- `0x0B`：flag
- `0x10` 开始为可选额外字符串
- 当 `flag != 0` 时，脚本流起点为额外字符串后的下一个字节

当前工具已能稳定导出：

- 载体头部
- 脚本流入口
- 指令 `offset`
- 指令 `next_offset`

## 文本载体

### 1. 直接字面量

`sub_4021F0` 当前已确认：

- `head >= 0x20`：直接读取 `cp932` 零结尾字面量
- `head == 0`：空串

这类文本通常是当前最适合优先处理的静态 patch 目标。

### 2. 字符串表引用

`sub_4021F0` 还会读取：

- `0x01..0x05`：1 字节索引引用
- `0x06..0x0B`：2 字节索引引用
- `0x0C..0x1F`：表达式索引引用

formal 工具会保留：

- `index_expr`
- `index_const`（可折叠时）

运行时字符串表当前只确认：

- `kind=1` -> `str19`
- `kind=3` -> `str18`

其他 kind 在运行时回退为空串。

### 3. 参数包参与的字符串

`sub_404880` 当前已确认：

- `kind == 1`：字符串参数，走 `sub_4021F0`
- 其余非零 kind：数值参数，走表达式机

因此，部分文本并不是孤立字符串，而是某条指令参数包的一部分。

## 为什么变长文本会卡住

当前主要死结不是“编码回写”，而是“布局变化”：

- 很多文本直接内联在脚本字节流里
- 文本变长后，后续指令的字节位置会整体后移
- 一旦位置变化，所有引用这些位置的控制流目标都必须重算

这意味着长文本写回不能只靠“替换字符串”，必须带上静态重定位。

## 偏移敏感字段白名单

后续 writer 只对白名单里的字段做重定位。

当前确认会用到脚本偏移的位置：

- 所有 decoder 已显式产出 `targets` 的控制流指令
- `switch_goto` 的 case 表项
- `call-like` 跳转目标（当前包括 `0x06`、`0x09`、`0x0A`）

当前确认**不要**当脚本偏移处理的字段：

- `sub_4021F0` 的字符串表索引
- `0x5E` 中的资源 ID / 资源引用参数
- 资源槽 ID、对象 ID、字符串表 index 这类数据字段

后续规则：

- 白名单内：允许重定位
- 白名单外但已确认是数据：保持原语义，不按偏移改写
- 未确认：直接拒绝写回，不做冒险修正

## 当前最重要的输出

### `main_disasm.py`

当前输出的 JSON 对静态写回有两类核心字段：

- `offset` / `next_offset`
- 控制流指令的 `targets`

这批字段是后续静态重定位的基础。

### `main_dump_text.py`

当前输出两类文本：

- `items`：当前可见字面量文本
- `resolved_items`：当前块链内已解引用成功的表引用文本

在现有代表样本里，主产物仍然以 `items` 为主。

## 当前边界

- 这套工具已经足够继续做“文本载体分类”和“偏移白名单整理”。
- 这套工具还不足以直接做完整变长写回。
- 当前主线不是继续深挖状态机，而是把 writer 所需的结构事实补齐。
