## HXP 读取链
### `Him4`

1. 读取 `entry_count`
2. 按顺序读取 `entry_offset`
3. 读取条目头：
   - `compressed_flag`
   - `unpacked_size`
4. 读取 payload

### `Him5`

1. 用名字跑 `0x408CC0`
2. 定位 bucket
3. 在 bucket blob 里顺序扫描记录
4. 取出 `entry_offset`
5. 再走统一条目读取逻辑

## 运行时脚本载体
### `0x401000`

当前已确认：

- `0x00..0x07`：`Himauri\0`
- `0x08..0x0A`：声明大小 `u24be`
- `0x0B`：flag
- `flag != 0` 时，`0x10` 起存在额外零结尾 ASCII 字符串
- 脚本流起点写入上下文 `+0x0C`
- 这个起点是相对整个 `Himauri` 缓冲区的偏移，不是相对数据段的二级偏移

### `0x404820`

当前已确认：

- 执行前把上一条偏移写到上下文 `+1760`
- 行号模式开启时，先读 `u16be` 到 `+1080`
- 然后读取 1 字节 opcode
- `0xFF` 为结束
- dispatch table 真实范围是 `0x00..0x71`
- `0x71 -> 0x405A00`，是 no-op handler

## 当前结论

- `HXP` 层现在已经足够支撑正式解包/回封工具
- `game/DATA` 中解出的 `Himauri` 条目，就是运行时喂给 `0x401000` 的脚本字节流
- `Himauri` 载体头部与调度器已经确认
- 当前脚本逆向的瓶颈不在包格式，而在 `0x401C60` 与一批变长 handler 的边界
