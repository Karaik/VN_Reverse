# 汉化流水线

## 范围与固定规则

用于新建、迁移或维护具体游戏的汉化工程。按本次交付选择相应步骤。

1. 每次构建仅清理本构建器已认证的旧生成产物，保留本地原版、译文、静态资源、缓存输入、未知手工文件和原有存档。
2. 正式构建输入按项目约定定位。可由项目配置指定原版路径和外部工具，记录必要的工具版本。
3. 文档命令以游戏项目根目录为基准，使用相对路径。
4. 无回归结果不得宣称完成。
5. 脚本验收应能从可编辑译文得到游戏可读的结果，验证范围与本次采用的回写方式一致。

## 游戏项目布局

除非已有更明确的项目约定，采用以下结构：

```text
title-root/
  README.md
  main_key.py
  main_unpack.py
  main_build.py
  game/
  game_script/
    translated_script/
      scn/
  solution/
    decrypt/
    unpack/
    build/
      build_cleanup.py
      README.md
    patch/
      base/
        chs_patch/
        chs_patch_manifest.txt
    runtime/
  out/
    package_<run_id>/
    validation_<run_id>/
```

- 根目录只保留必要入口，真正实现放在 `solution/`。
- 分离解密、解包、构建、静态补丁和运行时源码。
- 游戏需要格式参数或密钥时，记录其来源和本项目的读取入口。
- `game/` 是本地输入，不是待提交产物。
- `solution/build/` 是构建源码目录，不是可清理的构建产物。
- `out/` 是示例输出根，可按项目调整；清理只涉及其下已认证的顶层目录，绝不删除整个根。

## 逆向与脚本顺序

1. 确认引擎。
2. 确认归档或容器格式。
3. 确认脚本格式。
4. 确认编码与控制序列。
5. 资源使用加密或文件名映射时，确认本作所需的参数和映射来源。
6. 理解脚本与资源加载之后，再确定运行时补丁方案。

先从目标版本确认哪份资源实际生效，特别是补丁包优先于原包、多个作品共用文件名的情况。用旧版汉化做适配时，核对本次会复用的脚本字段、图片引用、音乐索引或加载顺序，只调整已确认的版本差异。

交付完整指令级逆向时，同时输出可编辑 JSON 和可读指令源码。汉化项目可以复用现成工具、文本字段回写或已有资源覆盖入口。原地替换验证编码后的长度上限，支持变长的编译器重算相关长度、偏移和表项。原样构建能稳定复现的格式按字节比对，工具会重排内部表或重新压缩时，比较解码后的结构、引用和值。

### 文本提取与回交

- 译稿同时有表格、TXT 或编译用 JSON 时，先确认构建读取哪份正式输入。回交后从选定稿生成派生文件，重新导出时保留已有译文。
- 从原脚本逐类清点正文、显示名、选项以及实际存在的标题、系统文字。用原结构的数量和位置独立核对导出，避免导出器与回填器同时漏掉一类记录，回环仍然通过。
- 保留现有译稿的编号、原文行和控制符。相同原文可能出现在不同场景或选项中，按本作的记录键和字段映射定位。顺序编号的项目，导出与回填须以相同顺序遍历场景内各类字段。显示名与逻辑角色 ID 分开写。
- 接收部分译稿或校对报告时，对照交付时的原文、编号与当前稿，只合入有对应位置的修改。编号重复、缺失或同一条已有另一版修改时，列出冲突。分别统计手工改动、已有规则的自动修正和未命中项。
- 换行、缩进和行宽按本作的显示方式检查。先区分说话人、对白、旁白和选项，再识别可见文本与排版控制符。仅检查时输出报告，保留原稿中的控制符，分别报告真实换行点和整条文本结尾。

## 编码与过滤

- 区分 `cp932`、`Shift_JIS`、`win-31j`、UTF-16 和 UTF-8。
- 分别确认原版读取编码、编辑文件编码和游戏回写编码。旧编码游戏采用 `gbk` 时，文档给出用法，并核对可显示字符和仍需源编码的控制序列。Unicode 游戏沿用实际文本编码。
- 项目已约定用 `filter_text.txt` 过滤编码时，按 UTF-8 逐行读取，并由项目明确采用精确匹配或子串匹配。
- 命中过滤条目的文本按源编码回写，其余文本按请求的目标编码回写。
- 启用过滤的项目同时验证命中和未命中的条目。

## 图片交付与回写

- 从构建器实际读取的图片或静态基底确定修图存放位置。沿用本作的目录和文件名，核对编辑图到游戏资源的对应关系。同名图片分布在多个包或图层时，保留包、路径、图层或帧编号。已有平铺替换机制的作品沿用其命名。
- 交付时说明应保留的相对路径、文件名、尺寸与透明通道。部分回交只替换收到的图片，其余沿用当前基线。图层坐标、资源引用、调色板或光标热点等按格式从原资源保留。
- 用回交图片重建对应资源，再从最终补丁解出比对。无损图像核对像素和透明度，有损格式按实际编码验证。涉及共享图层或多帧资源时，同时核对未改部分。再到标题、菜单等实际使用该图的界面确认显示。

## 运行时补丁

根据游戏选择资源覆盖、新启动程序加运行时 DLL、代理 DLL，或迁移现有可靠补丁布局。

- 可运行汉化交付所需的新运行时二进制从源码构建。
- 保留旧版二进制基底时，记录原始包来源、版本及文件摘要。有上游源码时附固定提交链接。
- 已有可靠覆盖范围与结构时沿用该行为，不重新猜测。
- KiriKiri 项目原有可靠方案若重定向到包，保留包重定向；覆盖文件由清单决定，不自动覆盖资源树中的全部内容。

## 构建前清理

按 `build-cleanup.md` 接入独立模块。每次构建或打包必须按以下顺序执行：

1. 解析项目根、显式输出根和本次 `run_id`，排除当前运行及本次输出。
2. 在生成新的完整游戏副本或包之前，列出并完整检查旧产物清理计划。
3. 默认清理已认证的旧构建、发布、打包与完整验证副本；`--keep-previous-outputs` 显式保留，`--dry-run` 仅展示计划并结束。
4. 清理成功后，通过 `generated_output(...)` 独占新建本轮目录。补丁按发布清单组装，实机验证需要完整游戏时再准备独立副本。
5. 上下文正常或异常退出时封存实际目录与文件清单；普通复制失败的半成品在下一轮可清理，原异常继续抛出。已有未知目录不得认领，进程强杀等未封存目录继续保留。
6. 运行验证；一次性副本内的测试存档、日志等可变位置必须提前逐项登记。

清理目标必须同时满足：位于项目内显式输出根的直接子目录、名称可识别、标记匹配本构建器和路径、普通文件清单与当前内容一致。输入目录、项目根、越界、异常名称、符号链接、联接点和重解析点全部拒绝；先完成整批预检，再由同一 Python 进程执行递归删除。清理失败时构建必须失败。

JSON 标记属于可信本地构建约定，不是防恶意伪造的签名认证；构建代码和输出目录需要由可信进程维护。

普通目录出现未知手工文件或修改后保留整个目录；副本内明确可变的文件或子树允许正常运行后继续清理，但仍检查所有链接。不得把原版存档或用户保留的存档列为可变产物。独立文件、上传压缩包、输入解包缓存、其他构建器或未认证的历史目录始终保留。禁止整删输出根、临时根或给未知旧目录补写认证标记。

新项目生成器复制模块与说明到 `solution/build/`，保留已有文件。接入现有项目时先比较本地版本；同一输出目录清理期间不得并发构建或运行。

## 文档

每个项目说明所用的资源格式和构建入口、正式输入、增量更新、最终包布局，以及构建前清理方式和调试保留开关。玩家首页可链接到已有开发笔记。

引用上游源码时使用固定提交链接。Mermaid 只在有助于理解时使用，并验证语法。

## 回归验证

按本次交付涉及的阶段验证：

1. 从回填后的脚本重读正文、显示名、选项等实际修改的字段，并核对相邻记录。
2. 重建归档时核对包内路径、条目数和替换内容。
3. 补丁分发时，从最终包取出文件，按玩家的安装方式在独立游戏目录验收，进入实际修改的场景或界面。
4. 使用编码过滤时，验证过滤回写。
5. 旧产物清理的边界、当前运行排除、调试保留和预览。

格式允许时验证逐字节一致；否则验证结构等价或运行时可读取，并为失败提供明确日志。重建归档应重新解包对比，重建脚本应重新反编译，代理 DLL 应验证导出，需要自定义存档重定向时验证路径行为。

清理回归使用真正临时目录，覆盖旧产物删除、受保护输入、越界、符号链接或联接点、陌生文件保留、显式可变位置、完整预检失败时零删除和当前输出排除。不得为了测试直接清理现有游戏项目的输出。

## 提交与完成边界

源码、文档、正式译稿、静态补丁输入和清单遵循该项目的版本控制约定。兼容基底记录来源，本轮生成的发布二进制随补丁分发，本地缓存留在工作目录。

打包完成后按发布清单核对实际文件和安装路径，排除开发材料、占位文件和构建归属标记。多作品仓库以本次发布的作品为准。加密交付时用约定的密码实际解压检查。

验收记录分别注明本次验证的脚本和资源范围、实机走到的位置、译稿进度及发布版本。抽样显示和全量回编分别计数。

## 最终发布与归档

所有汉化项目均须在汉化最终版对外发布前不久或发布后完成以下收尾。同一仓库分批发布多部作品时，在最后一批完成后执行。

1. 用最终译稿构建并验收补丁，留好这份成品作为最终 Release 附件。
2. 从 Git 跟踪的文件中逐项核对全部可编辑剧本文本，包括提取的原文、译文、双语对照稿及其副本。按内容确认范围，TXT、JSON 等格式都要检查。对核实的路径使用 `git rm --cached` 取消跟踪，保留本地工作稿、程序源码和工具。用普通提交记录删除并同步到作品仓库的默认分支，保留既有 Git 历史。
3. 核对远端清理提交的文件树，确认全部可编辑剧本文本均已移除。将最终标签指向该提交，发布 GitHub Release，附上第一步验收的补丁。
4. 核对 Release 的标签和附件后，在 GitHub 将该作品仓库设为 **Archived**（只读），完成归档。
