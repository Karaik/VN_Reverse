# 汉化项目规则

## 适用范围

适用于以“可维护的汉化构建链”和“可发布的汉化交付物”为目标的 title 项目。

典型信号：

- 存在 `main_build.py`
- 存在 `game_script/translated_script/`
- 存在 `solution/patch/`、`solution/runtime/`
- README 关注构建顺序、补丁输入、输出目录、冒烟测试

## 目标

汉化项目的完成标准不是“已经看懂格式”，而是：

- 译文输入路径稳定
- 构建链可重复执行
- 补丁资源与 runtime 来源清楚
- 可产出可验证的汉化包
- 增量更新文本和静态资源时不需要重新摸索流程

## 推荐目录

```text
title-root/
  README.md
  main_key.py
  main_unpack.py
  main_build.py
  game/
  game_script/
    translated_script/
  solution/
    decrypt/
    unpack/
    build/
    patch/
    runtime/
```

说明：

- 根目录只保留直接入口和必要说明。
- 真正的实现、静态补丁资源、runtime 源码、key 材料优先放在 `solution/` 下。
- `game/` 视为本地输入，不应被 README 描述成可提交产物。

## 必须回答的问题

每个汉化项目都应明确写清：

- 原版输入在哪里
- 译文输入在哪里
- 静态补丁资源在哪里
- runtime 是否需要从源码编译
- 输出目录长什么样
- 构建前如何清理旧生成产物，如何预览清理计划和显式保留旧输出
- 如何做只改文本、只改静态资源、首次完整构建

## 脚本与资源要求

- 如果脚本格式仍需要逆向，先补齐可编辑 roundtrip，再宣称脚本链完成。
- 如果脚本文本使用 `cp932`、`Shift_JIS`、`win-31j` 这类编码，必须有明确的回写编码策略；如需 `gbk` 路径，要在文档里显式写例子。
- 如果存在 `filter_text.txt` 语义，必须把过滤回写规则写进文档，并覆盖回归测试。
- 如果最终交付不只靠资源覆盖，还需要 `exe`、`dll` 或 proxy DLL，必须说明编译来源和验证方式。

## 验证要求

最少应覆盖：

- 文本输入到脚本回填的验证
- 资源或补丁包重建后的验证
- runtime 二进制构建或导出验证
- 最终可运行汉化包的冒烟验证

## 构建前清理

每次构建或打包，在产生新的完整游戏副本或包之前，必须先清理本构建器产生的旧构建、发布、打包及完整验证副本。新项目使用 `skills/galgame-localization/vn-localization-project/scripts/build_cleanup.py`；既有项目在下一次完整构建前也必须接入相同边界，不能继续新增没有归属登记的完整副本。

- 显式声明输出根，仅处理其直接子目录；名称必须能识别为构建产物，且以构建器归属标记与文件清单证明来源。名称相似不等于可以删除。
- 先严格解析并完整核对全部绝对路径和文件清单，再执行删除；拒绝项目根、越界、受保护输入，以及任意层级的符号链接、联接点和重解析点。Windows 上的递归删除必须在同一 Python 进程完成，不跨命令行解释器拼接路径。
- 原版、译文、静态补丁资源、输入解包缓存、上传压缩包、未知手工文件与原有存档均不在清理范围内；禁止整删 `out/`、临时目录或缓存根。
- 生成副本的普通内容新增或修改时保留整个目录。一次性验证副本内的测试存档、日志等确需运行时变化的位置，必须由构建器逐项登记为明确文件或子树；不得把原版或用户存档登记进去，可变位置同样拒绝链接。
- 当前运行使用新的 `run_id` 并排除本次输出；提供 `--keep-previous-outputs` 显式保留旧输出，提供 `--dry-run` 展示计划并在创建新完整副本前结束。
- 未登记的历史输出和其他构建器的产物默认保留；遇到不安全路径或清理失败时中止构建。清理期间不允许并发改写同一输出目录。

通过 `generated_output(...)` 独占新建本轮输出，正常或异常退出时封存实际清单，使普通复制失败的半成品也能在下一轮清理；原异常继续抛出，不在失败处理期间删除目录。已有未知目录、强杀后未封存目录不得补写标记。JSON 归属标记是可信本地流程约定，不抵抗恶意伪造。接入示例见 `skills/galgame-localization/vn-localization-project/references/build-cleanup.md`，生成器会将模块和说明复制到新项目的 `solution/build/`，并保留已有文件。

## 不要混入的内容

- 不要把纯逆向研究日志当成汉化项目的主流程文档。
- 不要把临时目录、手工搬运目录写成正式默认路径。
- 不要把“给 AI 的执行说明”继续塞到 README 的折叠块里。
