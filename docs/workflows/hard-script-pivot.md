# 困难脚本的止损与汉化优先策略

## 适用场景

适用于这类脚本逆向场景：

- 状态机很多
- 控制流高度间接
- switch / branch / handler 语义非常分散
- 很难在短期内做出可信的完整反编译器和编译器
- 但文本载体、文本引用或部分跳转关系已经能定位

这类项目的短期目标不应继续是“完整 script IR”，而应切到“可维护的汉化 patch 方案”。

## 什么时候立刻停止完整重构

满足下面两类条件中的任意一类，就应暂停“脚本本身的完整重构逆向”：

### 结构性阻塞

- 主要难点已经从“字段未确认”变成“状态机和 CFG 爆炸”
- 入口可解，但块边界、分支语义、case 过滤长期不稳定
- 没法在合理时间内给出可信的完整回编链

### 交付优先级反转

- 文本范围、文本引用、文本长度约束已经能定位
- 已经存在不需要完整 IR 也能推进汉化的替代方案
- 继续追完整逆向对当前交付帮助很小

一旦触发，不再把“完整脚本编译器”设为当前阶段阻塞项。

## 转向后的总原则

1. 保持原控制流，不主动重写脚本调度逻辑。
2. 只围绕文本替换、文本搬移、文本重定向做最小侵入改动。
3. 优先选择最便宜、最稳、最容易验证的方法。
4. 每个方法都必须写清前提、限制、失败条件、验证方式。
5. 当前目标是可交付汉化，不是把脚本研究做漂亮。

## 方法清单

### 方法 1：原地覆盖

适用条件：

- 能稳定定位文本位置
- 译文编码后长度小于等于原长度
- 原位置写回不会破坏后续数据

做法：

- 直接把译文 patch 回原偏移
- 保留原长度边界
- 必要时用原格式允许的填充字节补齐

优点：

- 实现最便宜
- 对控制流零侵入
- 最容易验证

限制：

- 受原长度严格限制
- 对中译通常空间非常紧

### 方法 2：短文本原地，超长文本外置重定向

适用条件：

- 短文本能原地覆盖
- 少量长文本需要额外空间
- 可以识别文本引用位置、长度字段或指针

做法：

- 先尽量原地覆盖所有短文本
- 对超长文本建立新的文本区或附加区
- 把原引用重定向到新位置

这是困难脚本里最常见也最实用的方案之一。

### 方法 3：在脚本末尾 append 新文本区

适用条件：

- 可以确认脚本末尾后面可以安全追加
- 能定位文本表、偏移表、指针或引用字段

做法：

- 在脚本或对应数据载体末尾追加新的文本节
- 为超长译文分配新偏移
- 回写原记录中的偏移和长度，使其指向新节

优点：

- 不需要完整恢复整份脚本控制流
- 只需要稳定掌握文本记录和引用关系

限制：

- 需要确认末尾追加不会影响校验、段表、索引表或压缩布局

### 方法 4：复用 padding、空洞、未使用区

适用条件：

- 文件中存在可确认的 code cave、padding、空洞、废弃表项

做法：

- 把长文本或跳板写入这些空洞
- 重定向引用过去

优点：

- 不必改文件总长度时尤其有用

限制：

- 可用空间通常碎片化
- 需要非常确定这些区域不会被运行时读取

### 方法 5：append 新指令块或跳板块

适用条件：

- 文本不是独立字符串池，而是混在脚本指令里
- 可以识别某些跳转、call、文本 opcode 的最小语义

做法：

- 保留原脚本主体
- 在末尾追加新的文本承载块或跳板块
- 让原位置改为跳到新块，执行完后再回原流程

典型用途：

- 原文本区空间太小
- 需要为某条文本单独腾出更大空间

限制：

- 至少要足够理解相关指令的跳转与返回语义

### 方法 6：外置文本资源 + 运行时 hook

适用条件：

- 资源层 patch 难做
- 但运行时拿文本的调用点可以 hook

做法：

- 保留原脚本
- 把译文放在外部文本表、json、二进制表或 patch 包里
- 在运行时按文本 ID、偏移、哈希或上下文替换显示文本

优点：

- 对原脚本侵入最小
- 对高复杂状态机尤其有效

限制：

- 需要稳定的运行时拦截点
- 调试成本转移到 runtime

### 方法 7：资源层覆盖，不做脚本回编

适用条件：

- 游戏支持 override、patch archive、代理 DLL、外部资源优先级
- 可以在更高层接管文本资源

做法：

- 在资源层构造替换文件
- 通过 patch 包、覆盖目录或代理加载机制接入
- 避开原脚本的完整回编问题

## 选择顺序

默认建议从便宜到昂贵：

1. 原地覆盖
2. 短文本原地 + 长文本外置重定向
3. 末尾 append 新文本区
4. 复用空洞或 padding
5. append 新指令块或跳板块
6. 运行时 hook 外置文本
7. 资源层覆盖或更高层 patch

不是越“底层正确”越好，而是谁最稳、最省、最容易验证就先用谁。

## 转向后的交付要求

即使不做完整逆向，也要补齐这些文档：

- 当前为什么停止完整脚本重构
- 已确认的文本载体和引用关系
- 当前采用哪种 patch 方法
- 这种方法的输入、输出、限制和验证方式
- 哪些文本仍不能安全处理

## 验证要求

最少应覆盖：

- 原文文本可稳定定位
- 短文本 patch 后运行不崩
- 超长文本重定向后显示正确
- 相邻文本和控制流未被误伤
- 打包后或 runtime 注入后可重复验证

## 不该做的事

- 不要在已经明确转向后，继续把完整 IR 当成当前阻塞项。
- 不要为了“理论完整”推翻已经可工作的低侵入 patch 链。
- 不要同时并行推进三到四种 patch 方法而不先收敛主路线。

## 文档落点建议

转向发生后，至少在对应 title README 里加一段简要说明：

- 当前脚本属于困难脚本
- 当前阶段目标是汉化优先
- 采用的方法是什么
- 完整逆向暂不作为阻塞项
